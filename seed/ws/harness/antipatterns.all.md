# sl-shop 실패 사례집 — 한 줄 = 한 실패, append-only

> 이 프로젝트에서 실제로 게이트가 잡았거나 사람이 되돌린 것만 적는다. 원인(→)이 없는 줄은 적지 않는다. 산문은 SR 도시에의 STORY `## QA 결과`에 있다.

- 예약 FUNC 둘(가입 요청 API·인증코드 API)을 **ID만 보고** 구현했다 → 역할이 정반대로 붙었다. STORY 제목의 이름(`ID@도메인:이름`)을 먼저 읽는다. (SR-231 r1)
- 레이트리밋 판정을 위해 datasource URL에 `useAffectedRows=true`를 넣었다 → 전역 속성이라 다른 FUNC의 `decreaseStock` 반환값 의미가 바뀌어 qty=0 주문이 200→409로 회귀. 한 FUNC의 필요로 전역 계약을 바꾸지 않는다. (SR-231 r4)
- 인증코드 시도 횟수를 트랜잭션 안에서 올렸다 → 검증 실패로 롤백되면 카운터도 같이 사라져 무제한 대입. 카운터는 실패 경로에서도 남게 별도 트랜잭션/원자 UPDATE로. (SR-231 r2)
- 같은 행을 두 커넥션이 `SELECT … FOR UPDATE` 순서를 달리 잡았다 → 데드락. 락 순서를 한 곳(DAO)에 고정하고 동시성 테스트를 3회 단독 실행한다. (SR-231 r3)
- 재작업 지시가 "존재 판정 → 인증" 순서였다 → 회원 존재 오라클(응답 차이로 가입 여부 노출). 인증이 먼저, 실패 응답은 동일 코드·동일 시간. 사람 지시도 QA 대상이다. (SR-231 r5)
- 세션 변수(`SET @token`)를 여러 문장에 걸쳐 썼다 → 커넥션 풀에서 문장 사이에 커넥션이 바뀌어 값이 사라졌다. 한 문장 안에서 끝내거나 애플리케이션 변수로. (SR-231 r3)
- 스케줄러 잠금을 `synchronized`로 걸었다 → 다중 인스턴스에서 무의미하고 단일 인스턴스에서는 타이머 스레드를 막았다. DB 행 락 또는 `SELECT … FOR UPDATE SKIP LOCKED`. (SR-231 r5)
- `CREATE TABLE`을 `IF NOT EXISTS` 없이 기동 DDL에 넣었다 → 두 번째 기동에서 앱이 죽었다(마이그레이션 엔진 없음). 규칙 `ddl-idempotent`. (SR-231 r2)
- 신규 고객 화면(UIS-MBR-001)을 shop-api Thymeleaf에 만들었다 → SPA(shop-web)와 스토리북 회귀 밖. 예약 폼의 구현 모듈을 지정한다(STORY 제약). (SR-231 r1)
- AIDD 잡이 도는 동안 `npm run dev`(HMR)를 켜 뒀다 → 에이전트 편집을 따라가며 3.2GB까지 커져 배경 작업이 OOM으로 죽었다. 잡 중에는 dev 서버를 내린다. (RUN7)
- 테스트 픽스처 SQL(`insert-out-of-stock.sql`)에 `linked_func` 주석이 없었다 → 축 A가 소속 불명으로 FAIL. 픽스처·SQL도 귀속 주석을 단다. (SR-230)
- 통합 테스트 두 개가 같은 리터럴 이메일로 매 실행 실패 로그인을 2회씩 남기면서 `@AfterEach`에서 그 카운터 행을 지우지 않았다 → 실행을 가로질러 `fail_count`가 누적돼 2~3회 실행마다 401 기대가 429로 깨지는 영구 플레이키. 잠금·레이트리밋처럼 "이메일/키 문자열이 PK인" 카운터 테이블은 테스트마다 고유 키를 쓰거나 그 행을 반드시 지운다. (SR-232 r2)
- API 키 DB 폴백 조회(`selectMemberIdByApiKey`)가 `MEMBER_API_KEYS` 단독 조회라 회원 존재·`del_yn`을 보지 않았다 → 탈퇴 회원이 로그인 때 발급받은 키가 탈퇴 후에도 무기한 API를 통과시켰다(이 코드베이스 전반의 `del_yn='N'` 상시필터 관례 위반). 회원 존재/자격 관련 키·토큰 조회는 항상 `MEMBERS` 조인 + `del_yn` 필터를 통과해야 한다. (SR-232 r2)
- 인증 필요 신규 컨트롤러(`MemberSessionController`)의 `@WebMvcTest`에 `AdminApiKeyTestConfig`를 import하지 않고 임의 문자열을 `X-Api-Key`로 썼다 → `ApiKeyAuthFilter`가 슬라이스에도 Filter 빈으로 딸려와 그 값이 정적 맵·DB 폴백 둘 다 미스라 컨트롤러 도달 전에 401로 막혔다(204/500 기대가 전부 401). 인증 필요 컨트롤러의 `@WebMvcTest`는 `CartControllerTest`처럼 `AdminApiKeyTestConfig`를 import한다. (SR-232 r3)
- STORY "테스트" 절 시나리오가 "로그아웃 뒤 같은 refreshToken으로 refresh → 200"을 서술했는데, 같은 STORY의 "005 인터페이스 경계표"(사람 확정, 재해석 금지)는 "로그아웃 = apiKey+리프레시 토큰 전체 폐기"였다 → 실제 코드(결정표 그대로 구현됨)와 테스트 서술이 모순돼 통합테스트가 매번 401로 깨졌다. 결정표가 서술보다 우선한다 — 코드가 아니라 테스트를 결정표에 맞춰 고친다. (SR-232 r3)
- ddd-api-agent가 한 INF 파일에 엔드포인트 2개(logout+refresh)를 담으며 frontmatter `path:`를 YAML 리스트로 썼다 → `spec_graph_build.py:105`가 `path.lower()`를 스칼라 문자열로 가정해 전체 스펙 그래프 빌드가 `AttributeError`로 죽었다(이 FUNC 하나가 아니라 전 프로젝트 스펙 그래프 영향). "1 INF = 1 엔드포인트" 관례를 스펙 형식 위반으로 깨지 말고 새 INF-ID로 분리한다. (SR-232, FUNC-member-006)
- 비밀번호 재설정 코드 요청 서비스가 "발송" 로그를 쿨다운 UPSERT(`touchRequest`)보다 먼저 무조건 남겼다 → 60초 안 재요청도 발송 이벤트가 또 남고, 실제 DB에 남은 해시와 방금 발송한 코드가 어긋났다. UPSERT 뒤 재조회한 `code_hash`가 방금 만든 해시와 같을 때만(=쿨다운에 걸리지 않았을 때만) 발송 로그를 남긴다(SR-231 round5 `last_token` 재조회 대조와 동일 기법). (SR-234 FUNC-member-008 r1)
- 비밀번호 재설정 화면의 유효시간·쿨다운 카운트다운이 `step`에 종속된 `useEffect`로 초 단위 상태를 직접 감소시켰다 → 3단계(새 비밀번호) 체류 중엔 시계가 멈춰, 코드 오류(409)로 2단계에 되돌아오면 실제 경과시간과 무관하게 잔여시간이 과대 표시됐다. 만료·쿨다운 표시는 `expiresAt`/`resendAvailableAt`(epoch ms)를 저장하고 매 tick `Date.now()` 차로 파생시킨다 — 표시가 걸리는 단계가 아니라 벽시계가 기준. (SR-234 FUNC-member-007 r1)
- 같은 화면의 confirm 오류 처리 switch가 미정의 코드(네트워크·5xx)를 `MBR-4100`과 같은 `default` 분기로 묶어 1단계로 되돌렸다 → AC 응답코드 표에 없는 전이가 새로 생겨, 일시적 서버 오류에도 사용자가 입력을 전부 잃었다. 오류 코드 분기는 계약표에 있는 코드만 명시적으로 매칭하고, 미정의 코드는 현재 단계 유지+재시도로 둔다(표에 없는 전이를 만들지 않는다). (SR-234 FUNC-member-007 r1)
- 재설정 코드 확정이 `attempt_count`를 "읽고 비교한 뒤 UPDATE"해 → 동시 오답 버스트가 상한(5)을 넘겨 시도할 수 있었다. 시도 횟수 증가는 단일 조건부 UPDATE(`SET attempt_count = attempt_count + 1 WHERE attempt_count < :max`)로 원자화하고, 0행일 때만 원인(행없음·소비·만료·상한)을 재조회해 오류 코드를 가른다. (SR-298 #1·#2)
- 만료된 재설정 코드 행을 정리 배치가 **즉시** 지우게 설계해 → 같은 테이블을 읽는 확정 API의 판정이 410(만료)에서 409(오답)로 바뀌어 화면 재요청 전이가 끊길 뻔했다(QA가 구현 뒤 발견). 행을 지우는 배치는 그 테이블을 **읽는 API의 오류 계약**부터 확인하고, 필요하면 보존 기간(여기선 만료 후 7일)을 둔다. (SR-297 #1)
- 정리 배치 DELETE 조건 컬럼(`expires_at`)에 인덱스가 없어 풀스캔·락 범위 확대 위험이 있었다 — 형제 배치(가입 `idx_msv_expires_at`)와 같이 인덱스를 함께 만든다. (SR-297 #1)
- 테이블 전역 DELETE를 검증하는 DAO 테스트가 영향행수를 절대값(=1)으로 단언해 → 다른 테스트가 남긴 만료 행이 있으면 깨지는 플레이키였다. 시딩한 UUID 행의 존재/부재를 재조회로 단언한다(형제 `MemberSignupRateLimitDaoTest`와 같은 방식). (SR-297 #1)
- 쿨다운+일일 상한을 한 UPSERT에 묶으면서 거부 사유 로그를 항상 "일일 상한 초과"로 남겨 → 최빈 케이스(발급 직후 재클릭 = 쿨다운)가 틀린 사유로 기록됐다. 재조회한 카운트로 사유를 가른다(`MemberSignupService#rejectionFor`와 같은 분기). (SR-297 #2)
- 자정 경계 테스트가 `Clock.fixed`로 시각만 주입하고 기본 허용 스텁을 그대로 둬 → 무조건 통과해 게이트 로직을 전혀 행사하지 않았다. 시간 의존 테스트는 호출 인자(dayKey·now)를 캡처해 단언한다. (SR-297 #2)
- 주문 조회 기본 창이 `LocalDate.now().minusDays(30)`인데 시드 주문 날짜가 고정이라 → 날짜가 흐르자 통합테스트 2건이 항상 실패하고, 이후 모든 SR의 기준선 게이트가 같은 실패로 멈췄다. 상대 조회창을 쓰는 화면·API의 테스트는 시계를 고정하거나 시드를 상대 날짜로 만든다. (SR-300 이월)
- 정적 리소스 핸들러(`ResourceHttpRequestHandler` + `PathResourceResolver`)로 SPA 폴백을 만들었는데, 매핑 패턴을 벗겨낸 나머지 경로가 빈 문자열이면(정확히 `/shop`·`/shop/`) 리졸버 진입 전에 자체 가드에서 404가 나 커스텀 폴백이 전혀 안 탔다(구현 후 MockMvc 실측으로 발견) → 경로 세그먼트 없는 루트 진입점은 별도 `@GetMapping` 컨트롤러로 처리한다. (SR-301 #1)
- 신규 컨트롤러를 `controller` 패키지가 아닌 `web`(필터·예외핸들러 전용) 패키지에 둬 `controller-has-test`(must) 규칙의 파일 경로 대상을 우회했다 → QA가 관례 이탈로 지적, 재작업으로 `controller` 패키지 이동+테스트 추가. 컨트롤러는 규칙이 검사하는 관례 위치에 둔다(파일명·클래스 성격이 아니라 규칙의 `paths` 패턴 기준). (SR-301 #1)
- QA CONCERNS 재작업 지시 "최초 진입 시만 리다이렉트"를 라우트 element 자체를 `<Navigate>`로 치환해 구현 → `pathname`이 세션 내내 불변이라 상시 리다이렉트가 되어 기존 화면(주문 목록)이 영구 도달 불가가 됐다(회귀). 진입점 제한 지시는 부팅 시 1회성 사이드이펙트(모듈 최상위, 렌더 이전)로 구현하고 라우트 자체는 건드리지 않는다. (SR-302 #1)
- 연타 방지(in-flight) 가드 테스트를 `fireEvent.click()` 3회 분리 호출로 작성 → 클릭 직후 버튼이 DOM에서 사라지는 구조 때문에 2·3번째 클릭이 빈 노드에 발사돼 가드를 지워도 테스트가 통과했다(거짓 보증). 연타 검증은 `act()` 한 스코프 안에서 flush 없이 묶어 발사하거나, 가드를 임시로 지운 뒤 테스트가 실제로 실패하는지 직접 재현해 확인한다. (SR-302 #1)
- 재동기화가 신규 화면 스펙을 만들 때 "다음 빈 번호"를 **자기 SR의 예약분까지 점유로 세어** 예약 ID(UIS-ORD-008)가 아니라 다음 번호(012)로 만들었다 → 항목 범위(예약 008)와 실제 스펙(012)이 어긋나 반영 게이트의 변경 이력 집계가 빗나갈 뻔했다. 신규 스펙은 **항목에 적힌 예약 ID 그대로** 만든다(번호를 다시 계산하지 않는다). (SR-302)
- 인증 필터의 공개 경로를 `isOpenRoute`(=`shouldNotFilter`) 화이트리스트에 추가했다 → 필터 자체가 스킵돼 키를 보낸 요청의 소유권 판정(`evaluateMemberScope`)까지 함께 우회되어 "키를 보낸 요청의 동작 불변" 회귀가 났다. 무인증을 "요구하지 않는" 것과 "판정을 스킵하는" 것은 다르다 — 무키 예외는 필터 본문(`doFilterInternal`) 안에서 "키 자체가 없을 때만" 처리한다. (SR-307 #1)
- 구현 계획의 "테스트" 절이 회귀 확인 범위를 `-Dtest=클래스1,클래스2`로 좁혀 지정했다 → QA가 `mvn -o test` 전체로 돌리자 계획이 못 본 기존 회귀 테스트(SR-301의 화이트리스트 누출 감시)가 정면 충돌해 깨졌다. 회귀 확인은 항상 스위트 전체로 하고, 계획에 좁힌 범위가 적혀 있어도 최종 확인 전에는 전체 실행으로 대체한다. (SR-307 #1)
- HEAD 요청 + 4xx 응답 조합을 `TestRestTemplate`(JDK `HttpURLConnection` 내장 팩토리)로 보냈다 → HEAD 응답은 본문이 없어 에러 스트림을 못 얻고 `IOException("Server returned HTTP response code: 401")`을 그대로 던져 테스트가 ERROR로 죽었다(단언 실패가 아니라 예외 — 필터는 실제로 401을 정확히 반환하고 있었음). PATCH와 동일한 JDK 한계이므로 HEAD/PATCH처럼 에러 스트림이 없거나 재시도 로직과 충돌하는 조합은 raw JDK `HttpClient`(`rawRequest` 헬퍼)로 보낸다. (SR-307 #1)
