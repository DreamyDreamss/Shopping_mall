# sl-shop 판단 기록 — 5줄 고정(정한 것/왜/틀렸으면 어떻게 아나/되돌리기)

## 기동 DDL은 Spring `sql.init` 재실행 + 멱등 스크립트로 한다 (SR-231 r2)
- **정한 것**: Flyway/Liquibase를 들이지 않고 `spring.sql.init.mode=always` + `db/*.sql`(IF NOT EXISTS · ADD COLUMN IF NOT EXISTS).
- **왜**: 랩 앱은 인스턴스 하나·개발 DB 하나다. 엔진을 들이면 버전 표·체크섬 관리가 늘고, 지금 필요한 것은 "기동하면 스키마가 맞다"뿐이다.
- **틀렸으면 어떻게 아나**: 컬럼 타입 변경·데이터 이관이 필요한 SR이 나오면(`ALTER … MODIFY`는 멱등이 아니다) — 그때 Flyway를 들이고 이 스크립트들을 V1로 옮긴다.
- **되돌리기**: `application.yml`의 `sql.init` 블록 삭제, `db/*.sql`을 Flyway `db/migration/`으로 이동.

## 신규 고객 화면은 shop-web(React), 관리자·기존 화면은 shop-api(Thymeleaf) (RUN7 #22)
- **정한 것**: 백로그 63건 중 고객 화면은 예약 시 구현 모듈을 `shop-web`으로 지정한다. 관리자 화면(SR-279~284)은 Thymeleaf에 둔다.
- **왜**: 스토리북(축 E)과 화면 상태 기준선은 shop-web에만 있다. 고객 화면을 서버 렌더로 만들면 화면 회귀를 도구가 못 잡는다.
- **틀렸으면 어떻게 아나**: 고객 화면이 두 모듈에 반씩 생겨 공통 헤더·탭바(SR-288)를 두 번 만들게 되면 — 모듈 경계를 잘못 그은 것이다.
- **되돌리기**: 예약 폼의 모듈 선택을 비우고(STORY 제약 제거) 이 결정을 지운다.

## 레이트리밋·시도 횟수는 요청 토큰 재조회 방식, 전역 커넥션 속성은 쓰지 않는다 (SR-231 r4→r5)
- **정한 것**: `MemberSignupRateLimitDao`는 `last_token`을 다시 읽어 판정한다. datasource URL의 `useAffectedRows`는 제거.
- **왜**: affected-rows 의미를 바꾸는 전역 속성이 다른 FUNC의 재고 차감 판정을 깨뜨렸다(QA 실측).
- **틀렸으면 어떻게 아나**: 재조회 방식이 동시 요청에서 상한을 1회 초과 허용하면(동시성 테스트 3회 단독 실행 중 1회라도) — 조건부 단일 UPDATE로 바꾼다.
- **되돌리기**: 없음 — 전역 속성으로는 돌아가지 않는다.

## 2026-09-13 — 걸린 SR 22건은 원장 단계를 형상(커밋)에 맞춘다
- **정한 것**: 커밋이 있는 18건은 CLOSED, 백로그가 확장·흡수하는 3건은 SUPERSEDED(217→271, 212→246, 211→283/274), 형상 0건인 213은 ON_HOLD.
- **왜**: 원장이 "IN_DEV·IN_QA"라고 말하는데 코드는 이미 커밋돼 있었다 — 단계가 사실을 안 따라가면 다음 실증이 같은 SR을 다시 판다.
- **틀렸으면 어떻게 아나**: 종결한 SR의 기능이 앱에서 동작하지 않거나(회귀 TC 실패), SUPERSEDED로 보낸 요구가 후속 SR 요지에 없다면.
- **되돌리기**: `sr_ledger.py revert`로 단계 되돌리기(history의 F2 노트가 근거). SUPERSEDED는 되돌릴 수 없다 — 새 SR로 다시 접수.

## 2026-09-13 — 비밀번호 재설정 코드 요청 API에 일일 상한·정리 배치를 두지 않는다 (SR-234 FUNC-008 r1 medium 수용)
- **정한 것**: target별 60초 쿨다운만. 일일 상한·만료 행 정리 배치는 후속 SR로 이월.
- **왜**: SR-234 요구 요지가 쿨다운만 말한다. 무인증 쓰기 경로라 위험은 알지만, 범위 밖 기능을 게이트 안에서 끼워 넣으면 라운드가 는다(RUN7 실측).
- **틀렸으면 어떻게 아나**: 운영 로그에서 같은 target 외 다수 target으로 분당 수십 건 발송 시뮬레이션이 관측되면(스캔·남용).
- **되돌리기**: 후속 SR에서 MEMBER_SIGNUP_RATE_LIMITS와 같은 모양의 일일 카운터를 붙인다(형제 가입 API 구현 재사용).

## 2026-09-13 — 코드 요청 응답 expiresInSeconds는 상수 600 (SR-234 FUNC-008 r2 권고 4 수용)
- **정한 것**: 쿨다운으로 코드가 갱신되지 않은 요청에도 600을 돌려준다(실제 남은 시간은 최대 60초 짧을 수 있다).
- **왜**: 실제 남은 시간을 돌려주면 '갱신됐는가'가 응답으로 새어 쿨다운 상태 오라클이 된다. 존재·상태를 안 새게 하는 것이 정확한 초보다 우선.
- **틀렸으면 어떻게 아나**: 화면 카운트다운이 끝나기 전에 코드가 만료돼 사용자가 '만료됨'을 보는 불만이 실측되면.
- **되돌리기**: 응답에서 expiresInSeconds를 빼고 화면이 자체 10분 타이머를 쓴다.

## 2026-09-16 — 만료된 재설정 코드 행은 7일 보존 뒤 삭제한다 (SR-297 #1, QA 권고 1 사람 결정)
- **정한 것**: 정리 배치는 `expires_at < now - P7D`인 행만 지운다(설정값). 7일 이내 만료 코드로 확정을 시도하면 기존대로 410(MBR-4101), 7일 초과 뒤에는 409(MBR-4102)가 된다 — 알려진 동작으로 INF-MBR-007·BAT-MBR-001에 적는다.
- **왜**: 즉시 삭제는 "만료"와 "오답"을 구분하지 못하게 만들어 화면의 재요청 전이를 끊는다. 무기한 보존은 정리 배치의 목적(테이블 증가 억제)을 없앤다. 7일이면 사용자가 같은 코드를 다시 시도할 현실적 기간을 덮는다.
- **틀렸으면 어떻게 아나**: 만료 7일 초과 코드로 인한 409 문의가 생기거나, 반대로 7일 보존으로 테이블이 계속 커지면(정리 후에도 행 수 증가 추세) 기간을 조정한다.
- **되돌리기**: `member.password-reset.purge-retention`을 P0D로 두면 즉시 삭제(종전 계획)로 돌아간다.

## 2026-09-16 — 쿨다운 판정을 카운터 테이블에도 둔다(이중 판정 허용) (SR-297 #2)
- **정한 것**: 일일 상한 UPSERT에 쿨다운 조건을 함께 넣어 가입 레이트리밋과 같은 모양을 유지한다. 코드 테이블(`created_at`)의 쿨다운 판정은 그대로 둔다.
- **왜**: 두 판정이 같은 상수·같은 `now`로 함께 전진해 평시에는 어긋나지 않고, 형제 도메인과 모양이 같아 다음 변경자가 헷갈리지 않는다.
- **틀렸으면 어떻게 아나**: 자정 직전 요청 뒤 60초 안에 날짜가 바뀌면 카운터는 허용하고 코드 테이블은 거부해 **일일 카운트만 소비**된다 — 이 사례가 실제로 관측되면 쿨다운을 코드 테이블 한 곳으로 모은다.
- **되돌리기**: 카운터 UPSERT에서 쿨다운 조건을 빼고 상한만 판정한다.

## 2026-09-17 — INF-ORD-017 ID 충돌은 재배정하지 않고 그대로 쓴다 (SR-301 #1, QA CONCERNS round1 medium#1 사람 결정)
- **정한 것**: SR-301.1이 예약한 `INF-ORD-017`(쇼핑 SPA 정적 서빙)을 그대로 사용한다. SR-212(`STORY-FUNC-order-016`, "상품 리뷰 API")가 과거 같은 ID를 예약했던 흔적은 재배정 없이 덮는다.
- **왜**: SR-212는 원장에서 SUPERSEDED(대체)로 claim(UIS-ORD-004)이 해제됐고, `STORY-FUNC-order-016`은 v5.1부터 실행 불가한 레거시 FUNC STORY(읽기 전용 이력)라 살아있는 점유가 아니다. `INF-ORD-017.md` 스펙 파일 자체가 이 SR 이전엔 존재하지 않아 실제로 비어 있었다.
- **틀렸으면 어떻게 아나**: SR-212가 실제로는 SUPERSEDED가 아니라 진행 예정으로 재활성화되거나, `STORY-FUNC-order-016`이 마이그레이션으로 실행 가능한 작업 항목으로 되살아나면(예: `migrate_v5.py`) — 그 시점에 이 SR 쪽을 새 ID로 재배정해야 한다.
- **되돌리기**: `INF-ORD-017.md`를 새 번호(예: `INF-ORD-018`)로 이동하고 코드 javadoc 7곳(ShopStaticResourceConfig·ShopIndexController·ApiKeyAuthFilter 주석·테스트 2종)의 참조를 일괄 치환한다.

## 2026-09-17 — story 예약 UIS ID(008)와 실제 생성 ID(012)가 갈리면 실제 값으로 정정하고 넘어간다 (SR-302 #1, STEP 5.5 사람 최종 확인)
- **정한 것**: `build_story.py`가 이 항목 생성 시 예약한 `UIS-ORD-008`을 그대로 쓰지 않고, STEP 5.5 `spec_resync_check`(zero-LLM 순번 배정)가 실제로 만든 `UIS-ORD-012`를 정본으로 삼는다. story AC·"신규 스펙" 절을 012로 정정했다.
- **왜**: `UIS-ORD-009`~`011`을 SR-303·SR-304·SR-305가 이미 각자 story에서 예약해 뒀고(아직 파일은 없음), resync 스크립트는 충돌 방지를 위해 다음 빈 번호(012)로 건너뛰었다. story 생성 시점의 예약은 "다음 순번 추정"일 뿐 확정 배정이 아니다.
- **틀렸으면 어떻게 아나**: SR-303·304·305가 실제로 구현될 때 그쪽도 예약 번호(009~011)와 실제 생성 번호가 어긋나면, 이 규칙(실제 생성 값을 정본으로 삼고 story를 사후 정정)이 반복 발생하는 패턴이라는 뜻 — 그땐 `build_story.py`가 예약 시점에 이미 점유된 번호를 건너뛰도록 고치는 게 맞다.
- **되돌리기**: story AC의 UIS 참조를 008로 되돌리고 `UIS-ORD-012` 폴더를 008로 리네임 + 앵커·spec_history 재기재.

## 2026-09-17 — 상품 조회 공개는 화이트리스트가 아니라 필터 본문의 무키 예외로 (SR-307 #1, QA round1 FAIL → 사람 지시)
- **정한 것**: `ApiKeyAuthFilter`의 상품 조회 GET 공개를 `isOpenRoute`(=`shouldNotFilter`) 화이트리스트에 넣지 않는다. 필터는 이 경로에서도 항상 실행되고, `doFilterInternal` 안에서 "요청에 키 헤더 자체가 없을 때만" 인증 요구를 면제한다. 키를 보낸 요청(무효 키 포함)은 종전과 동일하게 `evaluateMemberScope`(소유권 판정)를 그대로 거친다.
- **왜**: round1(화이트리스트 방식)은 필터 자체를 스킵시켜 `GET /api/products?memberId=타인`을 member 키로 보내도 403→200으로 바뀌는 회귀를 냈다 — "키를 보낸 요청의 동작 불변"이라는 SR 확정 문답을 어겼다. "인증을 요구하지 않는다"와 "판정을 건너뛴다"는 다른 결정이고, 화이트리스트는 후자를 강제한다.
- **틀렸으면 어떻게 아나**: 향후 공개 경로에 memberId 같은 소유권 토큰이 실제로 실리는 경우(오늘의 `Product`는 아니다)가 생기면, "무키만 면제"로도 그 토큰 기반 판정이 무키 요청 자체에서 우회되는지 다시 확인해야 한다(현재는 무키면 애초에 판정 자체를 안 타므로 문제 없음).
- **되돌리기**: `doFilterInternal`의 무키 예외 분기를 지우고 `isPublicProductReadPath`를 `isOpenRoute`로 옮기면 round1 상태(화이트리스트)로 되돌아간다 — 단, 그러면 위 회귀가 재현된다는 것을 QA가 이미 실측했다.

## 2026-09-17 — 이미지 정적 서빙 인증 화이트리스트는 실제 서빙 경로로 좁힌다 (SR-306 #2, QA CONCERNS round1·round2 → 사람 재작업 지시)
- **정한 것**: `ApiKeyAuthFilter.isOpenRoute`의 이미지 화이트리스트를 `/images/`(전체) 대신 `/images/products/`(실제 서빙 위치)로 좁힌다. 경계는 `assertThat(status).isEqualTo(401)`처럼 단일 기대값으로 테스트가 고정한다.
- **왜**: 넓은 접두사(`/images/`)는 훗날 그 아래 인증이 필요한 API(업로드 등)가 생기면 자동으로 무인증이 되는 잠재 위험을 남긴다. 정적 자산은 소유권 판정이 필요 없어 화이트리스트 자체는 맞지만(SR-307 #1의 "판정 스킵" 문제와는 조건이 다름), 범위는 실제 서빙 위치로 최소화해야 한다.
- **틀렸으면 어떻게 아나**: `/images/` 아래 다른 정적 자산 디렉터리(예: `/images/banners/`)가 새로 생기면 이 접두사가 매번 개별 추가돼야 한다 — 그 빈도가 잦아지면 "정적 자산 전용 최상위 경로"(`/static-assets/**` 등)로 재설계한다.
- **되돌리기**: `isOpenRoute`의 조건을 `path.startsWith("/images/")`로 되돌리면 SR-306 #2 이전 상태로 복귀 — 단 이 경우 QA가 실측한 잠재 위험(향후 확장 시 자동 무인증)이 다시 열린다.

## 2026-09-17 — 할인율은 정수 연산으로, "이미지 로드 실패" 스토리는 깨진 data URI로 (SR-306 #1, QA FAIL round1·round3 → 사람 재작업 지시)
- **정한 것**: (1) 정가·판매가로 파생하는 할인율은 뺄셈·곱셈을 먼저 하고 나눗셈을 마지막 1회만 수행한다(`(listPrice-price)*100/listPrice`, `discountRate.ts`의 단일 함수로 집중). (2) 화면 상태로 "이미지 로드 실패"를 보여줘야 하는 스토리는 실제 404 경로 대신 디코드만 실패하는 깨진 data URI(`data:image/png;base64,AAAAAAAA`)를 쓴다 — 같은 `onError` 폴백을 검증하되 브라우저 콘솔에 네트워크 error를 남기지 않는다. (3) Storybook이 다른 저장소(shop-api)의 정적 자산을 참조해야 하면 사본을 만들지 않고 `.storybook/main.ts`의 `staticDirs`로 원본을 직접 가리킨다.
- **왜**: (1) 나눗셈을 먼저 하는 식은 부동소수점 반올림 오차로 내림 경계 아래로 떨어져 1~99% 구간 중 17개 비율이 1%p 낮게 표시됐다. (2) 축E(`story_gate.py`) 하네스는 "콘솔 error 1건 이상=스토리 깨짐"으로 판정하는데, 확정 요건(문답 9)이 요구하는 상태는 의도적으로 깨진 이미지라 실제 404를 쓰면 이 판정 기준과 구조적으로 충돌한다 — 상태를 지우는 것(스펙 위반)도, 판정 기준을 바꾸는 것(하네스 변경은 이 항목 범위 밖)도 아닌 제3의 길을 사람이 골랐다. (3) 사본은 원본(shop-api)과 어긋날 수 있어 정본을 참조하는 쪽을 우선한다.
- **틀렸으면 어떻게 아나**: (1) 정가·판매가가 매우 크거나(예: 1e15 이상) 부호 있는 다른 통화 단위를 다루게 되면 정수 연산도 오버플로 여지가 있는지 다시 확인한다.
