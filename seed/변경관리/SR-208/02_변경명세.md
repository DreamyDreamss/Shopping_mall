# SR-208 변경명세

## AS-IS → TO-BE 비교

### INF-ORD-003 (GET /api/orders — 주문 목록 조회)

- AS-IS:
  - 오류 응답 표(§오류 응답): `400 | 유효성 실패 | 파라미터 타입 오류(날짜 형식 포함) 또는 유효 조회기간 역전(effectiveStart > effectiveEnd)` — 사유 문구의 구체적 본문 텍스트는 스펙에 기재돼 있지 않다(코드·발생조건만 명세, 메시지 원문은 [미상]).
  - `startDate`/`endDate`는 각각 독립적으로 기본값이 적용된다(§요청 파라미터, §비즈니스 규칙) — 종료일만 입력 시 `startDate`는 서버가 "오늘-30일"로 독립 보정.
  - 유효 구간 역전 시 400으로 거부(§비즈니스 규칙 마지막 항).
  - 응답 스키마(`totalCount`/`page`/`items[]`), 오류 코드 체계(400/401)는 SR-205 반영 이후 안정.
- TO-BE:
  - `OrderService.list`의 400 사유 문구만 개선 — 종료일만 입력된 경우, **사용자가 입력한 적 없는 서버 계산 `startDate`(예: 보정된 "오늘-30일" 값)를 역전 사유로 제시하지 않는다.** 대신 "기본값(최근 30일) 적용" 사실과 사용자가 취할 행동(예: 시작일을 함께 지정)을 안내하는 문구로 교체한다.
  - 오류 코드(400/401/5xx)·엔드포인트·파라미터 목록·응답 스키마(`totalCount`/`page`/`items[]`)는 **변경 없음** — 확정 문답(api_error)에 따라 신규 코드 없음, 기존 계약 유지. 확정 문답(api_compat: "필요 — 필드 추가만")은 하위호환 원칙이며, 이번 변경이 메시지 본문 텍스트만 바꾸는 한 신규 필드 추가는 불필요([미상] 실제 응답 바디에 사유 문구를 담는 필드명 — 스펙에 오류 응답 바디 스키마 예시가 없어 확정 불가, 구현 시 기존 필드 그대로 사용해야 함).
  - 5xx는 이번에도 흡수하지 않고 그대로 전파(요구 요지, Critical Rule 1 유지 — 스펙 변경 없음).

### UIS-ORD-001 (주문 목록, route: /order/list)

- AS-IS:
  - §2 시나리오 4: "조회 구간이 역전 등으로 서버가 4xx를 반환하면, 화면 상단에 '조회 실패: {사유}' 오류 배너가 표시되고 **목록은 비어있는 상태로 렌더된다**"(즉, 오류 시에도 결과 그리드가 렌더됨).
  - §3 블록 표: ① 오류 배너(4xx 조건부 표시), ③ 주문목록 그리드(표시조건 미기재 — 암묵적 상시 렌더), ④ 결과 요약("빈 결과 안내 + 전체 건수").
  - §5 표시 조건: "조회 결과 없음" 문구의 표시조건은 `result['items']가 빈 목록일 때`뿐 — **오류 상태와 무관하게** 빈 목록이면 노출된다. "전체 N건" 라벨의 표시조건은 별도로 기재돼 있지 않다(상시 표시로 해석됨).
  - 오류 배너와 "조회 결과 없음"/"전체 N건"/그리드가 동시에 표시될 수 있는 상태 — 오류와 빈 결과가 화면상 구분되지 않는다.
- TO-BE:
  - §2 시나리오 4 문구 변경: 4xx 발생 시 "화면 상단에 오류 배너만 표시하고, '조회 결과 없음' 안내·'전체 N건' 총건수 라벨·결과 테이블(그리드)을 모두 숨긴다."
  - §5 표시 조건 갱신:
    - ③ 주문목록 그리드: `searchError`가 null일 때만 렌더(4xx 시 숨김) — 신규 표시조건 추가.
    - "조회 결과 없음" 문구: `searchError`가 null이고 `result['items']`가 빈 목록일 때만 표시(4xx 시 숨김) — 조건에 `searchError` null 전제 추가.
    - "전체 N건" 라벨: `searchError`가 null일 때만 표시(4xx 시 숨김) — 신규 표시조건 추가.
    - 오류 배너(①): 표시조건 변경 없음(`searchError`가 null이 아닐 때).
  - 정상 조회 결과 0건(오류 아님)인 경우의 표시는 **변경 없음** — 확정 문답(scr_empty_state)에 따라 종전대로 "조회 결과 없음" 안내 + "전체 0건" 표시를 유지한다.
  - 5xx는 그대로 흡수하지 않음 — 시나리오 4 괄호 문구("5xx는 그대로 전파되어 이 화면에서 흡수하지 않음") 변경 없음.

## 제외(변경 없음 명시)

- INF-ORD-003 — 요청 파라미터(`memberId`/`orderState`/`startDate`/`endDate`/`page`/`size`), 응답 스키마(`totalCount`/`page`/`items[]`), 오류 코드 체계(400/401/5xx), 인증·인가 정책(§인증·인가): 확정 문답(api_error, api_compat)에 따라 기존 계약 유지 — 이번 SR은 400 사유 **문구**만 개선.
- UIS-ORD-001 — 검색조건 위젯(`memberId`/`#selState`/`#startDate`/`endDate`/`#btnSearch`), 그리드 컬럼(주문번호/회원/상태/총액/주문일시), 주문 상세 이동 링크(`/order/{orderNo}`): 요구 본문·확정 문답에 언급 없음, 변경 없음.
- `cart/list.html`, `product/detail.html` — 요구 요지에 "동일 패턴 표준화는 이번 범위에서 제외하고 별도 SR로 다룬다"고 명시. 해당 화면의 UIS 스펙은 이번 변경명세의 영향 스펙 목록에도 없어 대조 불가.
- UIS-ORD-002, UIS-ORD-003, UIS-ORD-004, UIS-ORD-005 — 확정 문답(scr_scope)에서 주문 도메인 화면 전체 목록으로 나열되어 "누락 화면 없음"을 확인하는 데 쓰였을 뿐, 요구 요지 본문은 `order/list.html`(=UIS-ORD-001) 외의 화면 변경을 기술하지 않는다. 이번 SR의 영향 스펙 파일 목록에도 포함되지 않아 AS-IS를 대조할 근거가 없다 — 실제로 변경이 필요한지는 [미상](해당 스펙 미Read).
- 타 도메인 테이블·집계(정산·통계류) — 확정 문답(db_ripple: "없음").
- 데이터 이관·백필 — 확정 문답(db_migration: "불필요(신규 데이터만)").

## 회귀 범위

- 확정 문답(regression_keep: "특정 화면/API만(명시)")에 따라, 회귀 검증 대상은 이번 변경이 직접 손대는 다음 두 스펙에 한정한다: INF-ORD-003(GET /api/orders 400 사유 문구 개선분 제외 전 계약), UIS-ORD-001(order/list.html의 오류 배너·그리드·결과요약 표시 로직).
- 정상 조회(성공 200) 시 그리드·"전체 N건"·페이징 동작은 변경 없이 유지돼야 한다.
- 정상 조회 결과 0건(오류 아님) 시 "조회 결과 없음" 안내 + "전체 0건" 표시는 종전대로 유지돼야 한다(확정 문답 scr_empty_state).
- 401(미인증)·5xx 응답의 처리(흡수하지 않고 그대로 전파)는 종전대로 유지돼야 한다(Critical Rule 1, 요구 요지 명시).
- 400 응답의 HTTP 코드·발생 조건(파라미터 타입 오류, 유효 조회기간 역전)은 변경 없이 유지돼야 한다 — 변경 대상은 사유 문구 본문뿐.
- 기존 클라이언트 하위호환 — 확정 문답(api_compat: "필요 — 필드 추가만")에 따라 기존 필드 제거·타입 변경 금지, 신규 필드가 필요해지면 추가만 허용.

## 롤백 요지

UIS-ORD-001에서 4xx 시 그리드·"조회 결과 없음" 안내·"전체 N건" 라벨을 숨기도록 추가한 표시조건(`searchError` null 전제)을 제거해 오류 상태에서도 종전처럼 그리드·안내·건수 라벨이 렌더되도록 되돌리고, `OrderService.list`의 400 사유 문구를 서버 계산 시작일을 노출하던 종전 문구로 되돌린다. 두 변경 모두 오류 코드·파라미터·응답 스키마를 건드리지 않으므로 API 계약 롤백은 불필요하며, 화면 템플릿과 서비스 메시지 조립 로직만 이전 버전으로 되돌리면 된다.
