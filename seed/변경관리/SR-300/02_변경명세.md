# SR-300 변경명세

## AS-IS → TO-BE 비교

### INF-ORD-003 (GET /api/orders — 주문 목록 조회)

- AS-IS: `startDate`/`endDate` 미제시 시 기본값 계산의 '오늘' 기준이 명시되어 있지 않다(스펙 서술: "미제시 시 종료일 기준 30일 전(오늘-30일)으로 독립 보정" / "미제시 시 오늘로 독립 보정" — 구현은 `OrderService.java:63` `LocalDate.now().minusDays(30)`로 시스템 시계를 직접 호출, 주입 지점 없음).
- TO-BE: '오늘'을 읽는 방법만 주입 가능한 `Clock`으로 바꾼다(기존 `MemberAddressService`의 Clock 주입 패턴 재사용). 운영 기본값은 시스템 시계이므로 운영 결과는 AS-IS와 동일 — 요청 파라미터·기본값 의미(최근 30일)·응답 스키마(`totalCount`/`page`/`items`)는 변경하지 않는다. 테스트는 고정 `Clock`으로 시드 주문일(2026-08-15~17) 기준 창을 재현해 날짜와 무관하게 통과한다.
- [미상]: 스펙 파일에는 `Clock` 주입 지점의 구체 시그니처(생성자 파라미터명·빈 등록 방식 등)가 실려 있지 않다 — 확정 문답도 "MemberAddressService 패턴 재사용"까지만 명시.

## 제외(변경 없음 명시)

- INF-ORD-003 요청 파라미터(`memberId`/`orderState`/`startDate`/`endDate`/`page`/`size`) — 확정 문답(api_compat)에 따라 요청 계약 불변
- INF-ORD-003 응답 스키마(`totalCount`/`page`/`items[]` 및 각 필드) — 확정 문답(api_compat)에 따라 응답 계약 불변
- INF-ORD-003 오류 응답(400 유효성 실패/역전, 401 인증 실패) 및 인증·인가 절 — 확정 문답(api_error)에 따라 오류 계약 불변, 새 코드 없음
- 기본 조회창 30일 정책 자체 — 확정 문답(scope_freeze)에서 명시적으로 범위 제외
- 시드 데이터 날짜 — 확정 문답(scope_freeze)에서 명시적으로 범위 제외
- SR-299(레이트리밋 행 정리) 등 다른 날짜/플레이키 이슈 — 확정 문답(scope_freeze)에서 명시적으로 범위 제외
- 프런트 변경 — 확정 문답(scope_freeze)에서 명시적으로 범위 제외
- 주문 엑셀 export 경로(null,null) 및 다른 서비스의 시계 사용 — 확정 문답(regression_keep)에서 유지 대상으로 명시, 이번 SR 변경 범위 아님

## 회귀 범위

- 기본 조회창(최근 30일, 양끝 포함) 불변
- `startDate`/`endDate` 두 파라미터 독립 보정 불변
- 유효 구간 역전 시 400과 기존 안내 문구 두 갈래(기본값 적용/명시 역전) 불변
- 응답 스키마(`totalCount`/`page`/`items`) 불변
- 명시 `startDate`/`endDate` 경로 불변
- 주문 엑셀 export 경로(null,null) 불변
- 다른 서비스의 시계 사용 불변(OrderService 외 서비스는 이번 SR 대상 아님)

(근거: 확정 문답 regression_keep)

## 롤백 요지

`OrderService.list`의 기본 조회창 계산에 주입한 `Clock`을 제거하고 `LocalDate.now().minusDays(30)` 직접 호출로 되돌리면 AS-IS 동작으로 복귀한다. 요청 파라미터·응답 스키마·오류 계약을 이번 SR에서 건드리지 않으므로 롤백 시 별도 계약 복원 작업은 없다. 단, 롤백 시 날짜 의존 테스트 3건(OrderListEndToEndIntegrationTest 2건·ApiKeyAuthIntegrationTest.memberApiKey_ordersListWithoutMemberIdParam_returnsOnlyOwnOrders)은 다시 날짜에 따라 실패할 수 있다(SR-298 원인 재발).
