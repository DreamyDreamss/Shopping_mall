# SR-203 의사결정 기록

## D6. 체크아웃 API·화면 계약 (2026-08-23)
- **개발팀 제안**:
  - REST: `POST /api/cart/checkout` {memberId} → 200 {orderNo, totalAmount, itemCount}.
    오류: 400(빈 장바구니 — "동작하지 않는다" 요구의 API 표현), 404(회원 없음),
    409(재고 부족 — 부족 품목별 사유 목록 포함, **전량 거부**).
  - 화면: 장바구니에 [주문하기] 폼(POST /cart/checkout) — 성공 시 redirect `/order/{orderNo}`
    (기존 주문 상세 화면 재사용), 실패 시 redirect `/cart` + flash 사유(PRG — 하우스 관례).
    빈 장바구니면 버튼 미노출.
  - **원자성**: 단일 트랜잭션(주문 생성=기존 OrderService 규칙 재사용·재고 차감·장바구니
    비우기) — 하나라도 실패하면 전부 롤백, 장바구니 보존.
- **결정**: 제안대로 확정. 결정자: 발주자 대행 [자기승인]

## D7. FUNC 구성 (2026-08-23, 분석가)
- 체크아웃은 **FUNC-order-012 단일 구현 단위**(API+화면 버튼·폼 — 반쪽 배포 불가한 한 기능).
  INF-ORD-014를 7-N `--new-inf`로 예약(이번 SR의 플러그인 검증 목표이기도 함).
- UIS-ORD-005(장바구니 화면)는 영향 스펙으로 claim하되, 그 FUNC(011)의 story는 코드 구현이
  없으므로 aidd에서 **[건너뛰기]** 처리 — 문서 갱신은 종결 단계 재생성이 담당.
- 주문 생성 규칙은 기존 OrderService 로직 재사용(새 규칙 금지 — 요구사항 명시).

## D8. itemCount 정의 추기 (2026-08-23, QA r1 지적)
- checkout 응답의 itemCount = **주문 품목 라인 수(distinct SKU)** — 총 수량(Σqty) 아님.
- 결정자: 발주자 대행 [자기승인] (dev 판단 추인 — D6 보완)

## D9. 409 사유 계열 확장 (2026-08-23, QA r2 권고 #2 후단)
- 체크아웃 409는 **재고 부족 + 판매중지(+미존재 상품)를 포괄하는 \'주문 불가 품목\' 계열**로 확정
  (D6 원문은 재고 부족만 명시 — 구현이 계약을 앞선 상태를 문서로 소급 정합).
- 메시지 접두어 통일(현행: 판매중지도 \'재고 부족:\' 접두어)은 후속 추적(비차단).
- INF-ORD-014 역생성 시 이 계열 정의가 반영돼야 한다.
- 결정자: 발주자 대행 [자기승인]
