# SR-297 변경명세

## AS-IS → TO-BE 비교

### INF-MBR-006 (POST /api/members/password-resets/codes — 비밀번호 재설정 코드 요청)

- AS-IS: 요청 파라미터는 `target`(Body, string, 필수) 하나뿐. 트랜잭션 순서는 (1) target 형식 검증 → (2) 채널 판별·정규화 → (3) 6자리 코드 생성·해시 → (4) `MEMBER_PASSWORD_RESETS` UPSERT(`touchRequest`, 쿨다운 60초 판정만) → (5) `selectByTarget` 재조회 → (6) 재조회 해시 일치 시에만 발송 로그 → (7) 202(`VerificationCodeResult`, `channel`/`target`/`expiresInSeconds`) 항상 동일 모양. 일일 요청 상한 개념 없음 — 쿨다운(60초)만 존재. 참조 테이블은 `MEMBER_PASSWORD_RESETS` 하나뿐.
- TO-BE: 요청 파라미터(`target`)·응답 모양(`channel`/`target`/`expiresInSeconds`)·오류 응답(`MBR-4100`/`MBR-5000`)은 **변경 없음**(하위호환 유지, 확정 문답 `api_compat`·`api_error`). 트랜잭션 순서에 target별 일일 요청 상한 5회 판정을 쿨다운 판정과 나란히 추가한다 — 신규 전용 카운터 테이블(`target`, `day_key` PK, 가입 `MEMBER_SIGNUP_RATE_LIMITS`와 같은 모양) 단일 UPSERT로 원자 판정한다(확정 문답 `scope_freeze`). 상한 초과 시에도 발송·코드 갱신만 생략하고 응답은 그대로 202·동일 바디(존재 오라클·쿨다운 오라클과 같은 이유로 상한 오라클도 만들지 않음, 확정 문답 `regression_keep`). 새 오류 코드는 만들지 않는다(확정 문답 `api_error`) — 상한 초과는 서버 로그로만 남긴다. 참조 테이블이 `MEMBER_PASSWORD_RESETS` + 신규 카운터 테이블(SCH-ID [미상], BAT-MBR-001 항목에서 함께 정의) 2개로 늘어난다.

### SCH-MBR-005 (MEMBER_PASSWORD_RESETS)

- AS-IS: 컬럼 `target`(PK)/`code_hash`/`expires_at`/`consumed_at`/`attempt_count`/`created_at` 6개. 인덱스 없음. `inf: [INF-MBR-006, INF-MBR-007]`.
- TO-BE: 테이블 스키마 자체는 **변경 없음**(컬럼·타입·NULL·기본값·PK 그대로) — 이 SR이 이 테이블에 미치는 유일한 영향은 만료 행 정리 배치(BAT-MBR-001)의 조건부 DELETE(`expires_at < now`) 대상이 된다는 점뿐(확정 문답 `db_ripple`, `bat_idempotent`). 스키마·다른 도메인 참조 변경 없음. 신규 카운터 테이블은 이 SCH의 확장이 아니라 별도 테이블(BAT-MBR-001 작업 항목에서 신설, SCH-ID [미상])이다.

### BAT-MBR-001 (신규 — 비밀번호 재설정 만료 행 정리 배치)

- AS-IS: 해당 스펙 없음 — 기존에 이 배치가 존재하지 않음(신규 생성, `docs/변경관리/SR-297/_impact.json`의 `new_specs`).
- TO-BE: `@Scheduled` 일 1회(새벽, 주기는 설정값) 배치를 신설한다(확정 문답 `bat_idempotent`). 처리 대상 둘: ① `MEMBER_PASSWORD_RESETS`에서 만료된 재설정 코드 행(`expires_at < now`) ② 신규 카운터 테이블에서 지난 날짜 카운터 행(`day_key < 오늘`). 두 DELETE 모두 조건부(시각·날짜 비교)라 재실행·중복 실행해도 결과가 같다(멱등) — 요청 경로(INF-MBR-006) 트랜잭션과는 분리된 별도 트랜잭션으로 수행한다. 가입 도메인의 레이트리밋·정리 배치는 이 배치와 무관하게 그대로 둔다(확정 문답 `regression_keep`, `scope_freeze`).

### 신규 카운터 테이블 (SCH-ID [미상] — 비밀번호 재설정 일일 요청 카운터)

- AS-IS: 해당 없음 — 신규 테이블(확정 문답 `scope_freeze`, `db_ripple`).
- TO-BE: `target`(PK) + `day_key`(PK) 복합키로 가입 `MEMBER_SIGNUP_RATE_LIMITS`(SCH-MBR-007)와 같은 모양 — 일일 카운트·최종 요청 시각 등 상한 판정에 필요한 컬럼을 갖는다(구체 컬럼 목록은 [미상], SCH-MBR-007 대응 컬럼을 참고해 승인 뒤 AIDD 재동기화 단계에서 확정). `target`별 일일 요청 상한 5회를 단일 UPSERT로 원자 판정한다. 빈 상태로 시작(오늘 카운트 0부터) — 이관·백필 없음(확정 문답 `db_migration`). 다른 도메인 테이블·집계(정산·통계류)에는 영향 없음(확정 문답 `db_ripple`).

## 제외(변경 없음 명시)

- 쿨다운 60초 값 — 확정 문답 `scope_freeze`에서 명시적으로 제외.
- 재설정 확정 API(FUNC-member-009, INF-MBR-007 등 확정 경로) — 확정 문답 `scope_freeze`에서 명시적으로 제외. `consumed_at`/`attempt_count` 처리는 그대로 이 API 소관.
- 가입 API(INF-MBR-001 등)·가입 정리 배치 — 확정 문답 `scope_freeze`, `regression_keep`에서 명시적으로 제외(불변).
- 화면(UIS) — 서버 전용 SR, 화면 변경 없음(확정 문답 `scr_scope`/`scr_empty_state`/`scr_states` — 범위 확정 문답의 "제외: 화면"이 유형 신호로 오감지된 문답이라는 주석, RUN13 수리).
- 오류 응답 계약(`MBR-4100`/`MBR-5000`) — 새 오류 코드를 만들지 않음(확정 문답 `api_error`).
- 요청·응답 형식(`target` 파라미터, `VerificationCodeResult` 바디 모양) — 하위호환 유지, 변경 없음(확정 문답 `api_compat`).

## 회귀 범위

- 코드 요청은 상한 초과·쿨다운·미가입 대상 모두 항상 202(존재 오라클 없음, 응답 본문 동일) — 확정 문답 `regression_keep`.
- 상한 이내 발급·확정 흐름 불변 — 확정 문답 `regression_keep`.
- 가입 레이트리밋·가입 정리 배치 불변 — 확정 문답 `regression_keep`.
- 기존 클라이언트 하위호환: 요청·응답 형식 변경 없음, 상한 초과 시에도 202(발송만 생략) — 확정 문답 `api_compat`.

## 롤백 요지

BAT-MBR-001(정리 배치)의 `@Scheduled` 등록을 해제하고 신규 카운터 테이블 참조 코드를 제거한 뒤, INF-MBR-006의 트랜잭션 순서에서 일일 상한 UPSERT 판정 단계를 제거해 쿨다운 판정만 남은 SR-297 이전 상태로 되돌린다. 신규 카운터 테이블 자체는 스키마 변경(DDL DROP 금지 규칙)이 아니므로 남겨두되 앱이 더 이상 참조하지 않게 하면 되고, `MEMBER_PASSWORD_RESETS`·기존 가입 도메인 테이블은 이 SR에서 스키마를 바꾸지 않았으므로 별도 원복이 불필요하다.
