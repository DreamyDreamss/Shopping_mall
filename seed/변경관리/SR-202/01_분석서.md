# SR-202 분석서

## SR 개요
- **SR**: SR-202 — 장바구니 도입 (담기·조회·수량변경·삭제)
- **SR 유형**: COMPOSITE (DB_CHANGE + API_NEW ×4 + SCREEN_NEW ×1 + SCREEN_MODIFY ×1)
- **우선순위**: High / **영향 도메인**: order / **분석일**: 2026-08-22 / **인입**: 로컬

## 요구사항 요약
상품을 회원별 장바구니에 담아 모아두는 중간 단계 도입. 담기(합산)·조회(합계)·수량변경(≥1)·
삭제·재고 초과/품절 방어. 서버 보관(회원ID 구분). 결제·주문 전환은 SR-203으로 분리.

## AS-IS 실측 (CIA + 소스/DB)
- 장바구니 개념 전무(테이블·API·화면 0 — grep/DB SHOW TABLES 실측).
- 상품 상세(UIS-ORD-004)는 조회 전용(액션 위젯 0 — spec §4 실측).
- 회원 데이터: MEMBERS 3건 + GET /api/members(INF-ORD-001) 존재 — 담기 폼 회원 선택에 활용.
- 재고 로직: PRODUCTS.stock_qty, 주문 생성이 decreaseStock 사용(장바구니는 재고를 차감하지
  않음 — 담기는 예약이 아니라 보관. 차감은 SR-203 체크아웃 몫으로 명시).

## 영향범위
| 구분 | AS-IS | 변경 유형 | 영향도 |
|------|-------|---------|--------|
| CART_ITEMS (신규 테이블) | 없음 | CREATE TABLE (D2 — PK(member_id,sku)·FK 2) | 중 |
| 장바구니 API 4종 (신규) | 없음 | POST/GET/PATCH/DELETE /api/cart* (D3) | 중 |
| UIS-ORD-005 (예약) | 없음 | 신규 — 장바구니 화면 | 중 |
| UIS-ORD-004 | 상세 조회 전용 | 담기 폼 추가 (SCREEN_MODIFY) | 하 |

**FUNC 스코핑(D5)**: API 4종은 별도 FUNC를 예약하지 않는다 — 구현 주체는 화면 FUNC 2개
(FUNC-order-010 **재개**: 담기 폼+POST 경로 / FUNC-order-011(신규 예약, UIS-ORD-005): 장바구니
화면+조회·변경·삭제 경로). INF 4종·SCH(CART_ITEMS)는 구현 후 `/sl-recon-inf`·`/sl-recon-sch`가
소스에서 채번·역생성한다(7-N 원칙). 스펙 파일을 찾지 말 것 — 이 문장이 그 근거다.

**회귀(ripple)**: PRODUCTS 소비처(INF-ORD-004/005/008/009 — 재고 차감·목록·상세), MEMBERS
소비처(INF-ORD-001/002). CART_ITEMS는 신규라 기존 쿼리 무영향 — 회귀 TC는 03_TC 참조.

**제외(무변경 명시)**: 기존 INF 9종 전부, SCH-ORD-001~005, UIS-ORD-001/002/003, 주문·회원 화면.

## 변경 요구사항 (SR 단일축)
- 담기: 회원+수량 지정, 같은 상품 합산, 재고 초과/품절 409 거부(사유 표시).
- 조회 화면: 품목(상품명·단가·수량·품목합계)+총합계, 빈 상태 문구+상품 목록 링크.
- 수량변경: ≥1 강제(D4 — <1은 400 거부+삭제 안내), 재고 초과 거부. 삭제: 명시적 버튼.
