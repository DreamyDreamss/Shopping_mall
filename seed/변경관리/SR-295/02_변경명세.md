# SR-295 변경명세

## AS-IS → TO-BE 비교

### INF-MBR-001 (POST /api/members/signup/verification-codes — 회원가입 인증코드 발송)

- AS-IS: 트랜잭션 순서 3단계 — `MEMBER_SIGNUP_VERIFICATIONS`에 원자 UPSERT(`writeCode`)로 "6자리 코드·만료시각을 기록"한다고만 명시. 같은 스펙의 비즈니스 규칙 절은 "`attempt_count`는 이 API가 컬럼만 소유하고 쓰지 않는다(FUNC-member-003 가입완료 API가 코드 검증 시 사용 예정)"고 명시 — 즉 `writeCode`는 `attempt_count`를 건드리지 않는다. `consumed_at`·`verified_at`에 대해서는 이 스펙에 기록 동작 언급이 없다(=writeCode가 건드린다는 근거도, 건드리지 않는다는 명시도 없음 — INF-MBR-002 쪽 부작용 서술로 미루어 실질적으로 비리셋 상태로 추정되나 이 스펙 파일 자체의 명문 근거는 [미상]). INF-MBR-002 "코드값 의미" 절이 이 상태를 "알려진 한계"로 교차 서술: "재발송(writeCode, FUNC-member-002 소유)이 attempt_count를 리셋하지 않아, 상한에 걸린 target은 재발송을 받아도 계속 MBR-4093"이며 회복은 코드 만료(5분)+정리배치(10분 주기)뿐.
- TO-BE: 같은 채널·타깃 행에 대한 재발송(`writeCode`) 시 6자리 코드·만료시각 갱신과 함께 **`attempt_count=0`, `consumed_at=NULL`, `verified_at=NULL`로 함께 리셋**한다. 요청·응답 파라미터·형식(`target` 입력, `{channel, target, expiresInSeconds}` 응답)은 변경 없음 — 서버 내부 쓰기 동작만 확장.

### INF-MBR-002 (POST /api/members/signup — 가입 요청(인증코드 검증 포함))

- AS-IS: STEP 1(`markVerifiedIfCodeMatches`) 조건부 UPDATE는 `channel`+`target`+`code`+미만료+`consumed_at IS NULL`+`verified_at IS NULL`+`attempt_count < 5`를 조건으로 매치한다. 재발송으로도 `attempt_count`가 리셋되지 않으므로, 이미 5 이상 도달한 target은 재발송 후에도 매 요청이 STEP 1 진입 시점 조건 검사에서 `attempt_count >= 5`로 걸려 `MBR-4093`을 계속 받는다(영구 잠금 — "알려진 한계"로 스펙에 명시). 자가치유는 코드 만료(5분)+정리배치(10분 주기)뿐.
- TO-BE: STEP 1 조건부 UPDATE 로직·조건식(`channel`+`target`+`code`+미만료+`consumed_at IS NULL`+`verified_at IS NULL`+`attempt_count < 5`), 3단계 흐름과 트랜잭션 경계, 오류코드·오류계약(`MBR-4091`/`MBR-4092`/`MBR-4093`/`MBR-4094`/`MBR-4001`/`MBR-5000`)은 **변경 없음**. INF-MBR-001의 재발송 리셋 덕분에, 잠긴(`attempt_count>=5`) target이 재발송을 받으면 새 코드 행은 `attempt_count=0`이므로 STEP 1 조건을 다시 만족해 정상 검증 가능해진다(=`MBR-4093` 회복 경로가 생김). STEP 1의 로직 자체는 그대로이고, INF-MBR-001이 써 두는 선행 상태만 바뀐다.

## 제외(변경 없음 명시)

- MEMBER_PASSWORD_RESETS(비밀번호 재설정 코드) — 확정 문답(scope_freeze)에서 이번 SR 범위 제외로 명시. 이 테이블·관련 로직은 INF-MBR-001/002 어디에도 등장하지 않으며 본 변경의 대상이 아니다.
- 레이트리밋 정책(MEMBER_SIGNUP_RATE_LIMITS, 60초 쿨다운·하루 5회 상한, 원자 UPSERT+토큰 재조회 판정) — 확정 문답(scope_freeze, regression_keep)에서 제외·회귀유지 대상으로 명시. INF-MBR-001의 해당 로직은 변경하지 않는다.
- 화면 — 확정 문답(scope_freeze)에서 제외 명시. INF-MBR-001/002 모두 `screens: []`로 서버 API만의 변경.
- 코드 만료 판정(`expires_at`, 5분/300초 고정값) — 확정 문답(regression_keep)에서 회귀유지 대상으로 명시. 값·판정 로직 변경 없음.
- 5회 오답 잠금 판정 로직 자체(INF-MBR-002 STEP 1 조건식·`incrementAttemptCount` 동작) — 확정 문답(regression_keep)에서 회귀유지 대상으로 명시. 조건식·판정 순서는 그대로이며, 그 조건을 만족시키는 선행 데이터 상태(재발송 시 리셋)만 바뀐다.
- 가입 성공 시 코드 소비(STEP 2 `consumed_at` UPDATE) — 확정 문답(regression_keep)에서 회귀유지 대상으로 명시. 변경 없음.
- INF-MBR-001/INF-MBR-002 요청·응답 파라미터 및 오류 응답 계약(코드·메시지·HTTP 상태·`login_url` 포함) — 확정 문답(api_compat, api_error)에서 하위호환·불변 대상으로 명시. 변경 없음.

## 회귀 범위

- 재발송 레이트리밋(MEMBER_SIGNUP_RATE_LIMITS: 60초 쿨다운·하루 5회 상한, quota 미소비 조건 포함)은 그대로 동작해야 한다.
- 코드 만료(`expires_at`, 5분) 판정은 그대로 동작해야 한다.
- 5회 오답 잠금 판정(INF-MBR-002 STEP 1, `attempt_count < 5` 조건·`incrementAttemptCount` 증가 로직)은 그대로 동작해야 한다.
- 가입 성공 시 코드 소비(`consumed_at` 세팅, STEP 2)는 그대로 동작해야 한다.
- INF-MBR-001/INF-MBR-002 응답 형식(성공·오류 모두)은 불변이어야 한다.
- (확정 문답 api_error 근거) 재발송 뒤에는 새 코드로 정상 검증되어 `MBR-4093`이 나오지 않아야 한다 — 이번 변경의 수용 기준이자 회귀 대상.

## 롤백 요지

`writeCode`(INF-MBR-001) UPSERT에서 `attempt_count=0`·`consumed_at=NULL`·`verified_at=NULL` 리셋 구문만 제거하고 기존 6자리 코드·만료시각 UPSERT만 남기면 AS-IS로 복귀한다. INF-MBR-002 STEP 1 조건식·오류계약은 이번 변경에서 건드리지 않으므로 별도 롤백 대상이 없다. 데이터 측면에서는 이미 리셋되어 검증 가능해진 기존 행이 있어도, 만료(5분)·정리배치(10분 주기)로 자연 정리되므로 별도 데이터 복구 절차는 불필요하다.
