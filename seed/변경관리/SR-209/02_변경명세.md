# SR-209 변경명세

## AS-IS → TO-BE 비교

### INF-ORD-003 (GET /api/orders — 주문 목록 조회, docs/05_설계서/order/INF/INF-ORD-003.md)

- AS-IS: 요청 파라미터는 `memberId`(Query, N)·`orderState`(Query, N)·`startDate`(Query, date, N, 미제시 시 종료일 기준 오늘−30일로 독립 보정)·`endDate`(Query, date, N, 미제시 시 오늘로 독립 보정)·`page`·`size` 6개. 응답 스키마는 `totalCount`/`page`/`items[]` 고정. 오류 응답은 400(유효성 실패 — 파라미터 타입 오류 또는 `effectiveStart` > `effectiveEnd`)·401(인증 실패) 2종.
- TO-BE: 변경 없음. 확정 문답(scope_freeze, api_compat, api_error)에 따라 API 계약(요청 파라미터·응답 스키마·오류 코드) 전부 그대로 유지한다. 화면(UIS-ORD-001)에서 프리셋 버튼 클릭 시 기존 `startDate`/`endDate` 파라미터에 계산된 날짜값을 채워 보내는 것뿐이며, 신규 파라미터·신규 응답 필드·신규 오류 코드는 없다.

### UIS-ORD-001 (주문 목록, docs/05_설계서/order/UIS/UIS-ORD-001_주문목록/spec.md)

> 참고: 현재 저장된 spec.md는 이미 v1.2(revision_history "SR-209 round13 재작업")로, 본문 내 `(SR-209)` 표기가 붙은 항목이 이번 SR로 추가되는 대상이다. 아래 AS-IS는 `(SR-209)` 표기가 없는 기존 요소, TO-BE는 `(SR-209)` 표기가 붙은 신규 요소를 근거로 구분했다.

- AS-IS(§2 시나리오): "주문 목록 조회" 시나리오 1개만 존재 — `memberId`/`orderState`/`startDate`/`endDate` 입력 후 `#btnSearch`로 `GET /order/list` 재요청.
- TO-BE(§2 시나리오): "조회기간 프리셋 버튼으로 빠른 조회 (SR-209)" 시나리오 신규 추가 — `#btnPreset7`/`#btnPreset30`/`#btnPreset90` 클릭 시 `applyOrderDatePreset(N)`이 `#startDate`/`#endDate`를 오늘 기준 N일 전~오늘로 채우고, 기존에 입력돼 있던 `memberId`/`orderState` 값은 그대로 둔 채 같은 `#searchForm`을 즉시 제출한다. 조회 결과·오류 처리는 기존 시나리오 1과 동일하게 동작(신규 API 파라미터·응답 필드·오류 코드 없음).

- AS-IS(§3 블록②/위젯표): 검색조건 블록의 위젯은 `memberId`(1)·`#selState`(2)·`#startDate`(3)·`endDate`(4)·`#btnSearch`(5) 5개.
- TO-BE(§3 블록②/위젯표): 검색조건 블록에 `#btnPreset7`(6, "최근 7일")·`#btnPreset30`(7, "최근 30일")·`#btnPreset90`(8, "최근 90일") 3개 버튼 신규 추가(button type=button, `applyOrderDatePreset(N)` 호출 → 폼 즉시 재제출). 그리드 위젯 "주문번호 링크"의 번호가 (6)→(9)로 재정렬.

- AS-IS(§5 표시조건): 오류 배너·주문목록 그리드·"조회 결과 없음"·"전체 N건" 4개 항목만 존재, 표시조건은 모두 `searchError` 값에 좌우.
- TO-BE(§5 표시조건): "조회기간 프리셋 버튼(`#btnPreset7`/`30`/`90`)" 행 신규 추가 — `searchError` 여부와 무관하게 항상 렌더(검색조건 블록 내 정적 버튼). 기존 4개 항목의 표시조건은 변경 없음.

## 제외(변경 없음 명시)

- INF-ORD-003 — 요청 파라미터·응답 스키마·오류 코드(400/401) 전부 불변. 화면에서 기존 `startDate`/`endDate` 파라미터를 채워 보내는 것뿐(확정 문답 scope_freeze, api_compat, api_error 근거).
- UIS-ORD-001 §1 화면 목적, §3 블록①(오류 배너)·③(주문목록 그리드, 위젯 번호 재정렬 제외)·④(결과 요약), §6 팝업·연계 화면, §7 데이터 출처·연결 — 문구·동작 변경 없음(단, ③은 그리드 링크 위젯 번호가 (6)→(9)로 밀림).
- UIS-ORD-001 §2 시나리오 1(기존 검색 조회)의 3~4단계(결과 표시·4xx 오류 배너·"조회 결과 없음")·§5 기존 4개 표시조건 행 — 조회 결과·정렬·페이징·상태 필터·빈 결과/오류 표기 전부 기존 그대로(확정 문답 regression_keep, scr_empty_state 근거).
- UIS-ORD-002, UIS-ORD-004, UIS-ORD-005 — 확정 문답(scr_scope)에서 이번 SR의 대상 화면으로 함께 나열됐으나, 이 초안 작업에 제공된 "영향 스펙 파일" 목록에는 포함되지 않아 스펙 원문을 Read하지 못했다. AS-IS/TO-BE 대조 불가 — [미상], 별도 확인 필요.

## 회귀 범위

- 확정 문답(regression_keep) 근거: 기존 조회 결과·정렬·페이징·상태 필터 전부 — SR-205(조회기간 필터 추가)·SR-208(4xx 시 그리드/안내/건수 라벨 숨김) 회귀 포함.
- 확정 문답(scr_empty_state) 근거: 조회 결과 0건 시 기존 "조회 결과 없음" 안내 유지, 4xx 응답 시 기존과 동일하게 오류 배너만 표시(그리드·안내·건수 라벨 숨김).
- 확정 문답(db_ripple, db_migration) 근거: 타 도메인 테이블·집계(정산·통계류) 파급 없음, 데이터 이관·백필 불필요 — DB/SCH 계층 회귀 대상 아님.
- INF-ORD-003의 기존 파라미터 보정 규칙(`startDate`/`endDate` 미제시 시 독립 보정, `effectiveStart` > `effectiveEnd` 시 400)과 인증·인가 정책(SR-204, `X-Api-Key`)은 이번 SR과 무관하게 그대로 회귀 대상.

## 롤백 요지

UIS-ORD-001 화면에서 프리셋 버튼 3개(`#btnPreset7`/`#btnPreset30`/`#btnPreset90`)와 `applyOrderDatePreset(N)` 스크립트, 관련 시나리오·표시조건 행을 제거하면 SR-209 이전 상태로 복귀한다. INF-ORD-003 API 계약은 이번 SR로 변경되지 않으므로 서버·DB 측 롤백 대상은 없다.
