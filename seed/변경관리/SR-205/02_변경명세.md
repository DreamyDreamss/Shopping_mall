# SR-205 변경명세

## AS-IS → TO-BE 비교

### INF-ORD-003 (GET /api/orders/ — 주문 목록 조회)

- AS-IS: 요청 파라미터는 `memberId`(Query, string, N), `orderState`(Query, string, N),
  `page`(Query, int, N, 기본 1), `size`(Query, int, N, 기본 20)의 4개뿐이다. 비즈니스 규칙상
  기간 조건은 없으며, `memberId`·`orderState`만 선택적으로 AND 필터된다. 응답 스키마는
  `totalCount`/`page`/`items[]`(각 item: orderNo·memberId·memberName·orderState·totalAmount·
  orderedAt·items·deliveries)이다. 오류 응답은 400(유효성 실패: 파라미터 타입 오류)·401(인증
  실패)만 명세돼 있다(500 공통 오류는 이 INF 문서에 별도 표기 없음).
- TO-BE: 조회 기간(시작~종료) 필터 파라미터를 요청에 **추가**한다(정확한 파라미터명은 요구사항·
  확정 문답에 명시되지 않아 `[미상]` — AIDD 설계 단계에서 확정 필요, 예: `startDate`/`endDate`
  또는 `orderedFrom`/`orderedTo` 형태로 추정되나 확정 아님). 파라미터 미제시 시 **기본값 = 최근
  30일**(오늘 기준 -30일 ~ 오늘, 정확한 경계 포함/제외 규칙은 `[미상]`)을 적용한다. 새 기간
  필터는 기존 `orderState` 필터와 **AND** 조건으로 결합한다(확정 문답 scope_freeze). 응답
  스키마(`totalCount`/`page`/`items[]` 및 각 필드)는 **변경하지 않는다** — 확정 문답 api_compat
  "필드 추가만(기존 호출 그대로 동작)"에 따라 요청 측에 파라미터가 추가될 뿐, 응답 필드는
  추가·변경 없이 기존 그대로 유지한다(확정 문답 regression_keep "데이터 계약 불변"). 오류
  응답 계약은 기존 그대로 400(파라미터 오류)·500(공통)을 유지한다(확정 문답 api_error) — 새
  파라미터의 형식 오류(예: 날짜 파싱 실패)도 기존 400 유효성 실패 계약에 편입되는 것으로
  본다(세부 메시지 문구는 `[미상]`).

### UIS-ORD-001 (주문 목록, /order/list)

- AS-IS: 검색조건 블록은 `memberId` 입력(1)·`selState` 드롭다운(2)·`btnSearch` 버튼(3) 3개
  위젯으로 구성되며, 폼(`#searchForm`, GET)이 `GET /order/list`로 재요청 시 `memberId`·
  `orderState` 쿼리 파라미터만 전달한다(§4). 빈 결과·오류 상태의 화면 표기는 spec에 별도
  기술이 없다(§8 "미확인 사항"은 페이징 UI 부재만 언급, 빈 결과/오류 배너 언급 없음).
- TO-BE: 검색조건 블록에 조회 기간(시작~종료) 입력 위젯을 **추가**한다(위젯 타입·정확한
  레이블·placeholder는 요구사항에 명시되지 않아 `[미상]` — 예: 시작일·종료일 두 개의 date
  입력, 기본값은 최근 30일 자동 채움 여부 포함 확정 문답에 명시 없음). 폼 제출(`btnSearch`,
  (3))이 `GET /order/list`로 재요청될 때 새 기간 파라미터가 `memberId`·`orderState`와 함께
  전송되어야 하며, 기간 필터는 기존 `orderState` 필터와 **AND**로 적용된다(scope_freeze).
  조회 결과가 없을 때는 "조회 결과 없음" 안내 문구를 표시하고, 오류 시에는 **기존 공통 오류
  배너**를 표시한다(확정 문답 scr_empty_state) — 이는 화면에 **신규로 추가되는 표기**다(AS-IS
  spec에 해당 표기 기술이 없었으므로, 기존 화면에 이미 있었는지 이번에 새로 만드는지는
  `[미상]`이며 최소한 명세 수준에서는 이번 SR로 명문화된다). 그 외 화면 구성(주문목록 테이블,
  총건수, 상세이동 링크 (4)~(8), 접근 권한 무게이팅)은 변경하지 않는다.

## 제외(변경 없음 명시)

- INF-ORD-003 응답 스키마(`totalCount`/`page`/`items[]` 및 하위 필드 전체) — 확정 문답
  api_compat·regression_keep에 따라 "기존 조회 결과 전부(데이터 계약 불변)", "필드 추가만"이
  명시적 요구이므로 응답 측 필드 추가·변경 없음.
- INF-ORD-003의 `memberId`·`orderState`·`page`·`size` 파라미터 의미·기본값 — 요구사항 범위에
  포함되지 않음(확정 문답 scope_freeze "제외: 요구 본문에 적히지 않은 것 전부").
- INF-ORD-003 오류 코드 체계(400/401, 신규 500 문구 포함) — 확정 문답 api_error "기존 목록
  API 오류 계약 그대로" — 코드·메시지 신설 없음.
- 타 도메인 테이블·집계(정산·통계류) — 확정 문답 db_ripple "없음".
- 기존 데이터 이관·백필 — 확정 문답 db_migration "불필요(신규 데이터만)".
- UIS-ORD-001의 주문목록 테이블 구성·상세이동 링크(4)~(8)·접근 권한(무게이팅) — 요구사항이
  검색조건 블록의 기간 필터 추가로 한정되어 있어 변경 없음.
- UIS-ORD-001 §8에 기술된 페이징 UI 부재 상태 — 이번 SR의 명시 범위 밖(확정 문답
  scr_scope "나열된 화면이 전부: UIS-ORD-001 주문 목록"이나, 요구 요지 자체가 기간 필터
  한정이므로 페이징은 별건).
- INF-ORD-003 인증·인가 정책(SR-204 전역 정책, `X-Api-Key`) — 이번 SR과 무관, 변경 없음.

## 회귀 범위

- 기존 조회 결과 전부(데이터 계약 불변) — 확정 문답 regression_keep을 그대로 근거로 한다.
  기간 필터 미지정 시에도 응답 스키마·필드는 동일해야 하며(단, 기본 최근 30일 적용으로 인해
  "필터 미지정 = 전체 기간 조회"였던 기존 동작 자체가 "필터 미지정 = 최근 30일 조회"로
  바뀌는 것은 요구사항의 의도된 변경이지 회귀가 아니다 — 다만 이 경계가 회귀 판정에서
  혼동되지 않도록 AIDD 단계에서 명확히 구분할 것).
- 기존 클라이언트 하위호환 — 확정 문답 api_compat "필드 추가만(기존 호출 그대로 동작)": 기간
  파라미터를 보내지 않는 기존 호출은 기존과 동일하게 동작해야 한다(단, 위 기본 30일 적용
  범위 변경은 예외로 요구사항에 포함됨).
- 오류 응답 계약 — 확정 문답 api_error: 기존 400/500 계약 유지, 신규 오류 코드 도입 금지.
- 타 도메인 파급 없음(db_ripple), 데이터 이관 불필요(db_migration) — 회귀 검증 범위에서
  정산·통계류 도메인은 제외.

## 롤백 요지

기간 필터 파라미터와 그 처리 로직(INF-ORD-003 요청단), 그리고 UIS-ORD-001 검색조건 블록의
기간 입력 위젯 및 관련 폼 전송 로직을 제거하면 SR-205 이전 상태로 복귀한다. 응답 스키마는
이번 변경에서 건드리지 않으므로(필드 추가 없음) 되돌릴 응답 계약이 없다. 빈 결과 안내 문구·
오류 배너 표기가 이번 SR로 신규 명문화된 것이라면 해당 표기 로직도 함께 제거한다. DB
스키마·타 도메인 변경이 없으므로(db_ripple 없음, db_migration 불필요) 데이터 되돌리기 절차는
불필요하다.
