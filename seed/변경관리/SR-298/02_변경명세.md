# SR-298 변경명세

## AS-IS → TO-BE 비교

### SR-298.1 — INF-MBR-002 (가입 요청/인증코드 검증 포함 · POST /api/members/signup)

- AS-IS: STEP 1(코드 검증)은 `MEMBER_SIGNUP_VERIFICATIONS`에 대해 `markVerifiedIfCodeMatches` 조건부 UPDATE(`channel`+`target`+`code`+미만료+`consumed_at IS NULL`+`verified_at IS NULL`+`attempt_count < 5`)를 먼저 실행한다. 이 UPDATE가 0행이면, 서비스가 **현재 `attempt_count`를 별도로 조회(읽기)**하여 이미 5 이상이면 증가 없이 409 `MBR-4093`, 아니면 `incrementAttemptCount`(별개의 두 번째 UPDATE 문)로 1 증가시킨 뒤 409 `MBR-4091`을 반환한다. 읽기(조회)와 증가(UPDATE)가 별개 문장이라 그 사이에 동시 요청이 끼어들면 여러 요청이 같은 "5 미만" 판단을 동시에 통과해 `attempt_count`가 5를 넘어설 수 있다(각 UPDATE는 autocommit 개별 문장).
- TO-BE: 시도 횟수 증가를 단일 조건부 UPDATE `attempt_count = attempt_count + 1 WHERE attempt_count < 5`(대상 조건: `channel`+`target`, 미만료/미소비/미검증 등 매치 조건은 기존 `markVerifiedIfCodeMatches`/`incrementAttemptCount`가 쓰던 것을 그대로 유지 — 정확한 WHERE 절 전체 구성은 [미상], 근거 파일에 SQL 원문 없음)로 원자화한다. 영향행수(affected rows)로 성공/실패를 판별 — 0행이면 이미 상한(5) 도달로 판단해 추가 조회 없이 409 `MBR-4093`, 1행이면 정상 증가 후 409 `MBR-4091`. STEP 1의 코드 검증 UPDATE(`markVerifiedIfCodeMatches`) 자체의 매치 조건·순서(존재 오라클 방지를 위한 STEP1→STEP0→STEP2 순서)는 변경 대상이 아니다.

### SR-298.2 — INF-MBR-007 (비밀번호 재설정 확정 · POST /api/members/password-resets/confirmations)

- AS-IS: `MEMBER_PASSWORD_RESETS`에 대해 코드 확정(`confirmIfCodeMatches`)과 시도 횟수 증가(문서상 "시도횟수 증가" UPDATE로 지칭, 정확한 메서드명은 [미상] — 스펙 텍스트는 "코드 확정/시도횟수 증가는 각각 autocommit 단일 UPDATE 문"이라고만 기술)가 **각각 별개의 autocommit 단일 UPDATE 문**으로 실행된다("실패 시도 카운터가 트랜잭션 롤백에 함께 사라지는 것을 방지"하기 위한 설계). 두 문장이 분리되어 있어 동시 요청이 같은 `attempt_count < 5` 판단을 함께 통과할 수 있다(SR-234/FUNC-member-009 QA 이월 사유).
- TO-BE: 시도 횟수 증가를 단일 조건부 UPDATE `attempt_count = attempt_count + 1 WHERE attempt_count < 5`로 원자화한다. 영향행수로 상한 도달 여부를 판별해 409 `MBR-4103`(코드 확인 시도 횟수 초과) 여부를 결정한다. 코드 확정(`confirmIfCodeMatches`) 자체의 매치 조건, `del_yn='N'` 이중 필터, 코드 확정이 회원 조회보다 항상 먼저 실행되는 순서(존재 오라클 방지), 1회용(`consumed_at`) 판정, 트랜잭션 경계(Writer 별도 빈)는 변경 대상이 아니다.

## 제외(변경 없음 명시)

- MBR-4093(INF-MBR-002), MBR-4103(INF-MBR-007) — 5회 초과 시 409 오류 코드·HTTP 상태·메시지 문구. 사유: 확정 문답(api_error) — "변경 없음, 5회 초과 409 계약 그대로".
- INF-MBR-002 STEP 1→STEP 0→STEP 2 순서 및 존재 오라클 방지 로직. 사유: 요구사항이 attempt_count 증가 문장의 원자화만 범위로 명시, 검증·판정 순서는 대상 아님.
- INF-MBR-007 코드 확정(`confirmIfCodeMatches`) 매치 조건, 회원 조회·비밀번호 반영·전 기기 로그아웃 트랜잭션 경계. 사유: 동일 — attempt_count 증가 문장만 대상.
- 요청/응답 파라미터, 응답 형식(JSON 필드, 204/201 등). 사유: 확정 문답(api_compat) — "요청·응답 형식 변경 없음(내부 SQL 원자화)".
- 레이트리밋, 코드 발급·만료 정책, 화면. 사유: 확정 문답(scope_freeze)에서 명시적으로 제외.
- `MEMBERS`, `MEMBER_SIGNUP_VERIFICATIONS`(consumed_at 소비 판정), `MEMBER_PASSWORD_RESETS`(consumed_at/expires_at 판정), `ID_SEQUENCES` 등 attempt_count 이외 컬럼·타 도메인 테이블. 사유: 확정 문답(db_ripple) — "두 테이블의 attempt_count 갱신 문장만 바뀐다".
- 스키마(DDL), 기존 데이터 이관·백필. 사유: 확정 문답(db_migration) — "스키마 변경 없음, 기존 attempt_count 컬럼 사용".

## 회귀 범위

- 5회 초과 시 409 유지: INF-MBR-002는 `MBR-4093`, INF-MBR-007은 `MBR-4103` — 기존 오류 코드·HTTP 상태 불변.
- 올바른 코드 1회 성공 — 정상 시나리오(코드 일치, 미만료, 미소비, `attempt_count < 5`)의 성공 경로(가입 완료/비밀번호 반영)는 변경 없이 유지.
- 코드 소비·만료 판정 불변 — `consumed_at`/`expires_at`/`verified_at` 조건과 그 판정 로직은 이번 SR의 변경 대상이 아님.
- 응답 형식 불변 — 요청/응답 바디, HTTP 상태, 오류 봉투(`{code, message}`, INF-MBR-002의 `login_url` 포함) 그대로.
- 동시성 회귀(신규 보장 대상): 동시 요청이 몰려도 성공(카운트 증가)은 최대 1회만 반영되고 나머지는 기존 오류 코드로 응답 — 원자화 UPDATE의 영향행수 판별로 보장.

## 롤백 요지

단일 조건부 UPDATE(`attempt_count = attempt_count + 1 WHERE attempt_count < 5`)를 원래의 2단계 패턴(INF-MBR-002: 읽기 조회 후 조건부 증가 UPDATE / INF-MBR-007: 별개의 확정 UPDATE·증가 UPDATE)으로 되돌리고, 영향행수 기반 분기 로직을 이전의 조회값 비교 기반 분기로 되돌린다. 두 INF 모두 attempt_count 갱신 문장 자체만 원복 대상이며, 매핑 파일(XML 매퍼)의 해당 문장과 이를 호출하는 서비스단 분기 코드만 되돌리면 된다 — 요청/응답 계약·오류 코드·트랜잭션 경계·스키마는 변경되지 않았으므로 추가 원복 대상이 없다.
